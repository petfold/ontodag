# Review of ontodag and loopmarket (2026-10-09)

A code, performance and design review of both repositories and of how they
fit together, done overnight on Peter's request ("go beyond code review ...
look at the principles and unique selling points of the projects and the
main goals, and evaluate to what extent and how those higher goals are
reflected (or not) in the code"; "also suggest ways of expanding the
coverage of the tests"). Discussion draft: the recommendations are
proposals, not decisions. Small defects found on the way were fixed and
tested; nothing was released.

**Method.** Two read-only surveys of the code (size, complexity, caches,
dead code, duplication, coupling), whose findings I reproduced before
relying on them; statement coverage of both suites (coverage.py); new
cross-kind fuzzing; differential tests across three writers (the eager
store, the same with its caches dropped, the sparse writer); a seeded
mutator of offer records; performance probes at realistic
sizes (ontodag's core pack plus all ten domain packs, 11,900 categories;
loopmarket books of 100 to 800 offers a side), each slow result profiled.
Versions: ontodag 0.30.7 + fixes, recordstore 0.22.1 + fix, loopmarket
0.14.4 + fixes. Machine: the i7-3612QM laptop, 8 GB.

## 1. Summary

The core idea of ontodag (a subsumption-only, canonical, mergeable
category store whose answers can be proved) is carried through the code
with real rigour: oracle tests, order-independence tests, certificates,
the contract with its versioned guarantees. Tonight's fuzzing across every
kind found no break of G1 (one root for equal knowledge) in the in-memory
DAG: 100 random worlds, each written in four orders and merged. The one
break it found was in the sparse writer (item 1). The weak spots are
elsewhere:

1. **Three released bugs, all fixed here.**
   - The sparse writer could commit a different root from the eager
     writer (an index it never fed).
   - `ontodag.migrate` silently dropped node metadata and payloads.
   - Removing a category that an `about` compound named made later
     writes and queries raise in the eager store, while the sparse writer
     accepted the same writes. A new differential test found it.

   Removal still leaves the terms that name a removed category in place,
   and what it should do with them is an open design question (§8).
2. **A performance cliff in recordstore**: one commit of more than about
   11,000 records took **over ten minutes** (quadratic eviction scan);
   fixed, now 1.1 s for 11,900 records.
3. **One announced book could stop every loopmarket reader's fold**
   (a malformed record, a number such as `1e999999999`, or a fake
   "clearing" book): fixed, now rejected with an attributed reason. A deeper gap remains open: the fold admits
   any announced clearing book's fills without checking them, so a
   self-consistent fake loop marks real offers filled for every reader
   (§4, §8).
4. **loopmarket's design says "ontodag is the one intersection engine",
   but the solver checks every give against every want**; the
   ontodag-indexed path exists only in tests. Its plan was to switch at a
   measured book size (gate G3). Measured tonight, the indexed path finds
   the same matches 8× faster already at 100 offers a side, and 13×
   faster at 400 and 800 (46 s → 3.5 s), so the threshold, if there is
   one, is below 100.
5. **The `odag` command on a large native store costs 9.6 s per call**
   (the whole file is re-reduced on every load); the query itself takes
   3 ms. (Decided and built the same day, §8 item 8: 0.66 s per call.)
6. **Complexity is concentrated, not spread**: `dag.py` (4,400 lines, one
   class of 131 methods, 20 lazily created caches) and the two CLIs
   (`odag` 3,100 lines; `loop` 4,800 lines, 39% of loopmarket's
   statements).
   The "core gains no further expressiveness" principle has held
   semantically (every kind is still a subsumption order) but not in
   code size: each kind added a share to one strongly connected cluster
   of methods. The sparse-writer bug came from exactly that structure.
7. **Compatibility is held together by private names and by spellings**:
   loopmarket hashes ontodag's canonical spellings into offer ids, and
   0.30.6/0.30.7 changed spellings while `CONTRACT_VERSION` stayed 0.4.
   Offer pins are compared with each other, never with the installed
   ontodag. (Decided and built the same day: spellings change only with
   the registry minor, §5; the private names have public forms, §8 item 7.)
8. **Tests are many and good (ontodag 1,261, loopmarket 327; 90% and 91%
   statement coverage), but CI never runs loopmarket's chain code**, the
   downstream gate covers ontodag-fs and not loopmarket, and some
   user-facing paths had no test at all (`odag`'s batch mode, until
   tonight).

## 2. Goals and how the code serves them

### 2.1 ontodag

| Principle (where it is stated) | In the code | Verdict |
|---|---|---|
| Canonical form: equal knowledge, equal root (G1, I2/I3) | Complete transitive reduction, re-reduction when terms move, re-spelling of stale compounds, oracle tests per kind; tonight's cross-kind fuzz: no break | **Strong.** The machinery that keeps it true is also the main source of complexity (§3.1) |
| Merge is a CRDT (I7, G2, G5) | `merge`, `merge_delta`, `sync`; commutativity fuzz | **Strong** for growth; removals and moves do not propagate, which is documented |
| Verifiable answers (CONTRACT §7) | `prove_below`/`verify_below` for `is_below`; recordstore proofs | **Holds** for `is_below`; `get` answers are not certified (documented) |
| Attributable (PROVENANCE) | Per-writer provenance stores, signed records, review | **Holds**; a claim about a compound relation term is lost from review when its spelling changes (the accepted price of 0.30.7) |
| Agents first (CONTRACT §1, AGENT_SURFACE) | `odag-mcp`, propose/confirm writes, canonical echo, `about` | **Holds**; the MCP module imports private CLI functions (`_make_backend`, `_resolve_store`) |
| The core stays dependency-free (B1) | Boundary tests check code *and* metadata; base install pure Python | **Strong** |
| Subsumption only; "the core gains no further expressiveness" (2026-08-01), one scoped exception (contract 0.2) | Nine kinds, role heads, narrower relations, family pins, all inside `OntoDAG` | **Semantically held, structurally not**: about 3,100 of `dag.py`'s 4,400 lines are in method groups that exist for dimensions or branch on them (§3.1) |
| Very large graphs; output-sensitive operations (Peter, 2026-10-06) | Hop indexes, planner, lazy reader | **Held for filing and queries** (put 1 ms, gets in ms at 11,900 categories); **not for whole-store operations**: the native load (9.3 s), the recordstore commit cliff (fixed), a solver step; nor for a broad `about` query (§6; decided and built the same day, §8 item 13) |

What is missing relative to the goals: a stated **complexity budget** for
the kinds. Every kind added since August was justified one at a time, and
each was correct, but the cost is paid in one class. The bugs found this
week all live where two parts meet, not in any one kind: two G1 breaks,
two hop-index gaps and the sparse-writer index (kinds and caches), and
the removed `about` constraint (one kind following another, and
removal).

## 3. Unnecessary complexity

### 3.1 ontodag

- **`dag.py`, one class doing fourteen jobs.** By the survey's grouping of
  `OntoDAG`'s methods: core DAG and counts (410 lines), memo and trip
  machinery (30), declarations (295), parsing (217), role heads (236),
  graph-ordered kinds (438), hop indexes (687), planner and `is_below`
  (583), `add_edge` and reduction (178), re-reduction and re-spelling
  (238), `put` and placement guards (239), remove, reclassify and cone
  removal (347), merge (34), derived DAGs (211). The groups from
  declarations to placement guards call each other in both directions, so
  they cannot be split into modules as they stand.
  The real decoupling is to make the dimension interpreter an object that
  owns its caches and is fed through one mutation seam.
- **Caches created on demand.** There are 53 `getattr(self, "_x", None)`
  sites over 20 attributes that `__init__` never declares. A subclass
  cannot see what it must maintain. That is how `SparseOntoDAG.add_node`
  came to skip the indexes (fixed with an explicit `_index_name` seam).
  `_heads_cache` and `_dim_cache` also depend on history in one corner
  case, a term-shaped head (recorded, not fixed).
- **Several ways to do one thing:**
  - Seven traversals are copied into `lazy.py` with `_expand` inserted,
    68–88% line-similar to the originals.
  - `merge_delta` is written twice (eager and sparse). Both copies had the
    falsy-store bug fixed tonight.
  - There are four routines that copy a DAG.
  - Query syntax is parsed three ways: CLI, web, MCP.
  - The CLI and the web app each have their own move logic, and the two
    differ: one canonicalizes, the other does not.
  - The identity check `nodes.get(p.name) is p` is written inline 24
    times, in nine modules.
- **Modes that multiply code paths:**
  - `_role_lenient` is read in 14 places.
  - `computed=` takes `True`, `False` or `self._lean`.
  - `_resident` switches between index and scan.
  - There are three re-entrancy guard sets plus a trip counter.
  - `_counts_frozen` switches count maintenance at six sites.
- **Legacy kept alive:**
  - `get_by_dag`, `prune_to_common_descendants` and `intersection_dag`
    serve only the classic page's `/dag/query/import` route. That route is
    untested and uses the name-based intersection that `viz.py` documents
    as wrong for typed terms. (The first two and the route were removed the
    same day, §8 item 3.)
  - `_remove_duplicate_root_edges` walks the ancestors of every top-level
    node on each merge. Its own comment says it fires only when merging
    onto a hydrated pre-0.15 store, which `migrate` repairs.
  - Six public constants and methods are unused.
  - `web/browser_check.py`, a Playwright dev script, ships in the wheel.
    (Moved to `scripts/` the same day, §8 item 3.)
- **Private names as the real API.** Other modules call `_canonical_name`
  (mcp 16 times, the CLI 3, loopmarket 1 until tonight). They also call
  `_parse_parametric` (5 modules), `_live_parent_names`, `_graph_parts`,
  `_contained_values` and `_computed_children`. mcp, web and migrate
  import private functions from `__main__`. A small public layer would
  remove this: `canonical(name)`, `parse_term(name)`, `parents_of(name)`,
  a store opener, and settings and backends modules.

### 3.2 loopmarket

- **`cli.py` is 39% of the statements** (4,800 lines, 209 top-level functions,
  56 subcommands, 43 settings). It mixes settings, the REPL, three
  grammars, the private-place layer, drafts, option pricing, the `watch`
  daemon, escrow and beat transactions, the sealed auction, announcements
  and register administration. Splitting it by area, with one session and
  settings module, would roughly halve the largest file. It would also
  stop logic from living only behind the CLI: the seven
  `Ontology.declare_*` methods are used only by tests, because the CLI
  seeds the catalogue its own way.
- **The same context, threaded everywhere.** `gate=` appears in 20
  signatures, `held=` in 13 and `available=` in 12. `MockClearing` takes
  12 parameters and `SolverAgent` has 18 fields. One "reads" object would
  carry them.
- **Record versions handled at the call sites:**
  - About ten call sites guard with `o.v >= 5 and o.bond is not None`.
  - Eight write `g.v >= 6 and g.underlying`, where the constructor already
    guarantees it.
  - v1/v2 support (GeoDisc, the haversine distance, overlap with a float
    epsilon) survives for records the chain verifier refuses (it accepts
    v4–v7), but the sister project circulator still writes v2.
  - The `loop/` record still writes the legacy `give` beside `gives`, and
    the leg format is parsed by hand in about 15 places. The `watch`
    composed-leg bug came from that (fixed).
- **Settings sprawl.** 43 settings and 86 reads. Validation is an if-chain
  inside `cmd_set`. `_guarantees` reads 20+ settings in 52 branches. `loop
  help` advertised 30 flags that did not exist (fixed: flags are now
  derived from the settings table).
- **Dead code (reported by the survey, high confidence):**
  `register.newest_reader`, `Ontology.assert_edge`, `TimeWindow.from_iso`,
  `Bond.payable`, `EscrowClient.ladder_at`, `SolverAgent.run`, the
  `ASK`/`BID`/`ask`/`bid` synonyms, and two fallback copies of
  `canonical_bytes` that differ from the real encoder.
- **Duplication:**
  - The web3 plumbing is copied in four clients and three deploy scripts.
  - Remaining capacity is computed three times.
  - Major versions are parsed twice.
  - The "apply the prelude if missing" block appears six times.
  - The odag CLI scaffolding is copied: the settings table, the config
    reader and the REPL.

### 3.3 Process complexity

- **`CLAUDE.md` has become a diary.** ontodag's is 2,332 lines and 35,000
  words; loopmarket's is 110 lines but 11,000 words. Each is loaded into
  every working session, and much of it is history now duplicated in
  CHANGELOG and the design records. A current-state guide of a few hundred
  lines would cut the cost of every session and the risk of acting on a
  stale paragraph. (Decided and built the same day, §8 item 6.)
- **The code carries its history too.** loopmarket's source has 162 dated
  notes and 32 mentions of Peter. Several are already stale: an error
  message still says `when(...)`, a comment says a place "carries its
  disc", and pyproject mentions `get(overlapping=)`. Dated notes belong in
  CHANGELOG. Comments should say what is true now. (The false ones fixed
  the same day, §8 item 6.)

## 5. Compatibility between the repositories

- **Offer identity rides on ontodag's spellings.**
  - Offer ids hash the canonical spellings ontodag gives the concepts.
  - G1 promises equal roots and G7 that answers never shrink within one
    major. Neither promises that a newer ontodag spells a term the same
    way.
  - 0.30.6 dropped redundant constraints that had been refused; 0.30.7
    re-spells stale relation compounds. Both kept `CONTRACT_VERSION` 0.4,
    which is defensible since no valid spelling changed meaning, but a
    consumer cannot tell.
  - **Recommendation:** a contract clause on spelling stability, saying
    that a spelling valid under a contract major keeps its canonical form
    unless the graph relates its constraints, and that a change of a valid
    spelling is a major bump. Count the spelling rules in the registry
    version's minor.
  - **Decided 2026-10-09 (Peter): signal, don't freeze** — contract 0.5's
    G8: a spelling or a stored form changes only with the registry minor,
    with the migrate step in CHANGELOG, enforced by a recorded fixture
    (CONTRACT.md §3). A stability promise within a major was declined: it
    would have made every canonical-form fix a major bump before 1.0.
- **Pins are checked against each other, never against the installed
  ontodag.** `_gates` compares a give's majors with a want's;
  `MockClearing.submit` checks only `ontology_root`. proof-fabric.md §3
  says clearing checks the pins against its own ontology.
  **Recommendation:** fail closed when an offer's registry or contract
  major differs from the installed `ontodag`'s.
- **Private and undocumented coupling:**
  - loopmarket uses `_OVERRIDES`, `_resolve_store`, `_normalize_spec` and
    `Session` from `ontodag.__main__`, and recordstore's private
    `_addressing_name`.
  - It also relies on undocumented shapes: `prelude.DECLARATIONS`,
    `dag.nodes`, `Item.parents`, `add_edge(Item, Item)`, `deepcopy`, and
    the declaration-graph layout.
  - It parses canonical spellings with its own regexes (time ranges with
    an inclusive `T23:59:59Z`, `duration(<n>s)`, `length(<n>m)`).
  - One private call was replaced tonight: `Ontology.argument` now uses
    the public `surface.elaborate`.
- **The three upstream asks are still open** (loopmarket's cli.md §11):
  coordinate input for `geo`, relative times, and a public store opener.
  The third would retire most of the private coupling above.
- **The two grammars disagree on durations.** `loop` reads `90m` as
  minutes and `1w` as a week, while ontodag reads `duration(90m)` as
  ninety *metres* and rejects `w`. That breaks loopmarket's own "one
  grammar" gate (cli.md §2).
- **Release coupling:**
  - ontodag-fs pins a ceiling and is tested by ontodag's `downstream`
    publish job.
  - loopmarket pins only a floor and is not tested there; 0.30.6 broke
    one of its tests.
  - **Recommendation:** run loopmarket's fast suite (without the chain
    tests) in the downstream job, or give loopmarket a ceiling.
- **Install drift on this machine.** The editable ontodag install
  reported an older version than its code. That is harmless, but floor
  checks on this machine read stale metadata.

      itself (its anchors list every term), or after a term whose hops

      checked against the scan by `TestTermsInsideAreAllOfThem`). Never
      for a head whose terms escape.

      its budget, instead of walking it to the end and dropping it.
    - **The planner.** A dimension term (other than the graph kind, which
      keeps its estimate) has no count to plan by, so it is walked only up
      to the smallest sized cone's size times the probe cost; past that it
      is probed. With no sized cone the terms race at budgets growing
      fourfold.

    unused intermediate meet that depends on the order. Measured on the
    committed code, one writer, every order of `crate` under
    `mass(1kg..6kg)`, `mass(3kg..9kg)`, `mass(2kg..5kg)`: two roots
    (`05fab491a9` in two orders, `9dabacee75` in four); both file the crate
    under `mass(3kg..5kg)`, and one also keeps an empty `mass(3kg..6kg)`.
    Merges in different groupings share it (`TestAMergeFilesAtTheMeet`
    compares stored forms less such values). A tension behind every fix:
    while the intermediate meet holds the crate it is an answer (`get
    mass(..10kg)` lists value nodes), and G2 says a merge never takes an
    answer away, so a replica that once held it must keep it, while G1
    says a replica that never did must reach the same root. Options:
    **A** — keep a value only while something is filed under it, or it is
    filed under an ordinary category: a fold, a move or a remove that
    leaves a value empty forgets it, and `put mass(3kg) mass` alone stores
    nothing (refused with a teaching error, as a write with no effect).
    Pros: the stored form is a function of what is filed, so any order,
    any merge grouping, one root; `x` under `mass(2kg..5kg)` and `x` under

    piece of knowledge, which the current rule stores two ways); `remove`
    undoes a value's filing. Cons: G2 and G7 need a sentence (a value node
    nothing is filed under any more can leave an answer; every item stays);
    listings stop showing unused values (loopmarket's and ontodag-fs's
    uses to check); stored forms change (can ride the unreleased 4.4).

    empty. Pros: keeps "a value once named stays" for named values. Cons:
    a new record field to merge and hash, history kept as data, and the
    same G2 sentence (a fold-made meet that held an item can still leave
    an answer). **C** — leave it, as documented now (CONTRACT.md G1's
    gap). Pros: no work. Cons: G1's gap stays for every item with three or
    more overlapping values of one head; equal knowledge, different
    roots. **D** — stop folding in storage (the planner intersects cones
    since §15). Pros: no meet nodes at all. Cons: declined in question 12;
    `x` under one value and `x` under two whose meet it is still differ.
    **Recommendation: A**, because it is the only option that makes the
    root a function of the knowledge, which is what G1 promises and what
    a content-addressed store needs; the G2 sentence it costs is about
    value nodes, which carry no fact of their own (the arithmetic answers
    a term whether or not its node exists). Not measured beyond the
    example: how many stores hold unused values, and what loopmarket and
    ontodag-fs list.
