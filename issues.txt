And how many ways to set settings: environment variable, command line option, stored settings file, set command. (any others?) Are all setting settable by all of these methods? Which take priority and which are durable?
  DONE 2026-08-02, and the honest answer to "are all settings settable all
  ways" was NO — so it was fixed rather than documented. There were three
  regimes: store had all four layers, the bee_* settings had no flag, and
  rendering had no config key. Now one table and one rule for all six
  (store, limit, render, bee_api, bee_batch, bee_signer):
      flag > environment > config file > default
  Durability is the clean way to choose between them: a flag lasts one
  command, an environment variable one shell, `odag set` forever (it writes
  ~/.ontodag/config). `odag set` with no arguments prints what is in
  effect, from whichever layer. `auto` is a real value meaning "decide from
  whether output is a terminal". Bad values are refused at set time, not at
  the next command that reads them. Guide §5.7.

cut part of a dag? what is it called, a view? or projection? not sure of the correct technical term
  ANSWERED (terminology only; no code yet). A query result is a principal
  down-set (order theory: ideal; graph theory: the descendant cone). For
  what you extract from it: "view" if live and derived, "excerpt" or
  "subgraph" if materialized. NOT "projection" — that's the relational
  operator that drops columns, not rows. Both halves already exist in code
  (intersection_dag = the view, copy_subdag = the excerpt); what's missing
  is only a command that names them.

visualise? Andras Aranyi worked on this. it's in the repo. Is this still up to date, tested? Can I use a normal browser (not curl) to use it? Does it work with new features? should be mentioned in User Guide
  DONE 2026-08-02 — and the answer to "does it work with new features" was
  NO. Three real bugs, all found by actually running it, all fixed:

  1. VISUALIZATION WAS BROKEN BY DIMENSIONS. Canonical parametric names were
     used as DOT node *identifiers*, and DOT reads `:` as a port separator —
     so time(2026-...T00:00:00Z..) split mid-name and graphviz died with a
     syntax error. Any store with a typed date could not be drawn at all:
     `odag visualize`, /dag/image, /dag/export/dot and /dag/export/tex were
     all dead. Fixed by putting names in labels and using synthetic ids
     (n0, n1, ...), which makes every name renderable whatever it contains.
  2. THE REST API COULD NOT BE USED ALONE. Session state was initialized
     only by the two page routes, so a curl-only client got a raw KeyError
     traceback. That was documented as a "gotcha" in the guide; documenting
     a traceback is not a fix. Endpoints now initialize what they need, and
     the gotcha is gone from the guide.
  3. THE UI DID NOT URL-ENCODE QUERY TERMS, so a name containing + & or #
     silently queried something else ("C++ notes" arrived as "C   notes").

  What DOES work, verified over HTTP: parametric values in both boxes,
  virtual query terms (weight(..5kg) with no such node), calendar dimensions,
  union with `|`, an empty query box (now everything), all four exports, both
  images, and the market demo. Two deliberate limitations now written into
  guide §6: the browser shows canonical names, not the friendly spellings
  (no renderer on the web surface), and the web app's DAG lives in server
  memory per session — it is not your odag store and cannot use Swarm.

  Tests: TestPicturesAndExports (tests/test_web.py) and
  TestVisualizerRendersEveryName (tests/testdag.py) — 6 tests that fail
  against the old code. There had been NO test coverage of any rendering
  endpoint, which is exactly why this survived the dimensions release.

  CLICKED THROUGH IN A REAL BROWSER (Brave, via the Claude extension) the
  same day, which found three MORE bugs that HTTP checks had missed —
  because the endpoints returned 200 with wrong or empty content:

  4. THE QUERY PICTURE IGNORED PARAMETRIC TERMS. It was built by
     get_by_dag, which intersects by NAME, so a virtual term simply
     dropped out. Querying weight(..5kg) drew an empty graph; worse,
     Japan,weight(..5kg) drew ALL of Japan — a picture contradicting the
     result list printed right beside it. Now built from get(), the
     authoritative path, with query terms drawn as nodes even when they
     have none of their own (the picture is a view: it is drawn and
     discarded, never merged, so inventing a node to draw is sound).
  5. THE QUERY PICTURE HAD NO UNION. It split on "," only, so
     Flight,Japan|Hotel drew one node literally named "Japan|Hotel".
     Now parses the same DNF as /dag/query and draws each branch.
  6. /market 500'd IN ANY SESSION THAT HAD USED THE MAIN PAGE. Both share
     the `my_dag` session key, and the demo only loaded the car ontology
     when that key was absent. Pre-existing (verified against the old
     code), but easier to hit now that every endpoint creates a DAG. Now
     it loads whenever the DAG present isn't a car one.

  Verified by eye: the picture redraws after each Add Item; click-to-
  enlarge overlay; query terms shaded differently from results; union as
  two branches; blank query = everything; Remove Item; the error modal on
  a bad parent; and the market demo intersecting Budget+ElectricVehicle
  down to one offer. No console errors.

  Lesson worth keeping: a 200 is not a pass. Bugs 4 and 5 both returned a
  valid PNG — one of them 83x59, which I had recorded as success.

should empty query means returning everything, not error?
  DONE 2026-08-02. Yes — the empty intersection is the universe, which also
  makes get() total. `odag get`, `odag list` and `odag get '*'` are now one
  code path; same for REST (`?cat=` absent) and MCP (`query` with neither
  argument). A dangling `or` is still an error: there the empty part is a
  typo, and reading it as "everything" would silently widen a narrow query.
  Two things came with it, because a query that can print the whole store
  needs them: `odag count [CAT...]` (one number, complete, never capped)
  and a display cap of 50 lines at a terminal — never in a pipe, `-n N` /
  `-n 0` to override, withheld count on stderr. MCP deliberately has NO
  default cap: an agent can't see a terminal, so it can't see a truncation
  either; it opts in with `limit` and is told (`truncated`, with `count`
  still reporting the complete size).
